## 一、判断对错（每题 1 分，共 10 分）

**1. ( T ) 流水线 CPU 设计可以提高指令执行的流量。**

✅ 正确。流水线通过重叠执行多条指令，提高了指令吞吐率（throughput，即单位时间完成的指令条数）。虽然单条指令的延迟（latency）不变甚至略有增加（流水寄存器开销），但吞吐率大幅提升。 [笔记19, 笔记20]

---

**2. ( T ) 在单周期数据通路中，被两寄存器指定的 "Read Addr 1" 和 "Read Addr 2" 总是处于读状态。**

✅ 正确。寄存器堆的读操作为组合逻辑——只要给定了读地址（Read Addr 1/2），对应的数据就会持续出现在 Read Data 1/2 输出端口上。无需读使能信号。读取结果是否被使用，由下游多路选择器决定。 [笔记18]

---

**3. ( F ) 在执行 LW 指令时，"Read Data 2" 的内容用于基地址。**

❌ 错误。LW 指令中：`rs` 提供基地址（Read Data 1），`rt` 是**目的寄存器**（加载的数据写入 rt）。Read Data 2 在 LW 中不被使用（或说使用其寄存器编号 rt 作为目标寄存器编号，而非数据值）。用于基地址的是 Read Data 1（来自 rs）。

---

**4. ( F ) 在单周期数据通路中，"MemRead" 信号和 "MemWrite" 信号可同时声明为有效。**

❌ 错误。单周期 CPU 中，MemRead 和 MemWrite 是互斥的——一条指令要么读存储器（LW），要么写存储器（SW），不可能同时读写。同时声明会导致总线冲突。

---

**5. ( T ) 两条连续的指令之间有数据冒险，如 "LW" 后跟着 "SW"，可以通过数据转发部件来解决。**

✅ 正确。`LW → SW` 的依赖关系是：LW 将数据写入 rt，SW 将 rt 的值存到内存。LW 在 MEM 段拿到数据，SW 在 EX 段计算地址、在 MEM 段写入数据。SW 的 MEM 段正好在 LW 的 WB 段之后——但对于 SW，它需要的源数据（要存的值）在 EX/MEM 流水寄存器中，可以通过转发路径从 MEM/WB 转发到 EX/MEM，供给 SW 的 MEM 段。实际上 LW→SW 是可以通过转发解决的（SW 在 MEM 阶段才需要数据，而 LW 在 MEM 阶段结束时已有数据）。

---

**6. ( F ) 在 5 段流水 CPU 设计中，"RegDst" 控制信号在 WB 阶段使用。**

❌ 错误。RegDst 控制信号用于选择写寄存器堆的目标寄存器编号——在 R 型指令中选 rd，I 型指令中选 rt。这个选择发生在 **ID 阶段**（确定目标寄存器编号），并随 ID/EX → EX/MEM → MEM/WB 流水寄存器逐级转发。它在 WB 阶段被*使用*来指定写入哪个寄存器，但 RegDst **控制信号的生成**在 ID 阶段，且信号值在 ID 阶段就确定了。题目可能考的是"RegDst 在哪个阶段决定"——应是 ID 阶段。

> 严格来说：RegDst 信号本身随流水线传递到 WB 阶段，用于选择 Write Register 的地址。但其值在 ID 阶段确定。若题目意为"RegDst 在 EX 阶段使用"（选择 ALU 的 rd 还是 rt），则是 EX 阶段。考虑到标准 MIPS 流水线数据通路图中 RegDst 的 MUX 在 ID/EX 流水寄存器之前（ID 段末尾），**RegDst 在 ID 段产生并锁存到 ID/EX，在 EX 段实际使用**（选择目标寄存器编号转发到 EX/MEM）。故"在 WB 阶段使用"是错误的。

---

**7. ( F ) 为了解决控制冒险，内存被分为 IM 和 DM 两部分。**

❌ 错误。指令存储器（IM）和数据存储器（DM）的分离是为了**解决结构冲突**而非控制冒险。如果 IM 和 DM 不分离，取指令（IF 段）和访存（MEM 段）会竞争同一个存储器端口，造成结构冲突。控制冒险由分支指令引起，通过**清空流水寄存器（flush）、延迟槽、提前分支判断到 ID 段**等机制解决。 [笔记20]

---

**8. ( T ) load-use 冒险可以在 LW 指令的 EXE 阶段被发现。**

✅ 正确。load-use 冒险的检测在 ID 阶段完成——当 ID 段的下一条指令需要用到正在 EX 段（或 MEM 段）执行的 LW 指令的目标寄存器时，冲突检测硬件在 ID 段比较寄存器编号并发出 stall 信号。但题目说"在 LW 指令的 EXE 阶段被发现"——从 LW 的视角看，它在 EX 阶段计算访存地址时，下一指令在 ID 阶段读寄存器，此时冲突检测硬件发现依赖并 stall。所以可以说该冒险在 LW 处于 EX 阶段时被检测到。 [笔记20]

---

**9. ( T ) 为了在 ID 阶段知道 Branch 指令的去向而减少 branch 延迟，存在 ID/EXE 流水器的 ALU 结果应该被转发到 ID 阶段。**

✅ 正确。为了将分支判断从 EX 段提前到 ID 段，需要在 ID 段就能拿到 rs 和 rt 的值进行比较。若分支指令依赖的寄存器值还在 EX/MEM 或 MEM/WB 流水寄存器中（尚未写回寄存器堆），就需要**转发路径**将前指令的 ALU 结果（或 MEM 数据）旁路到 ID 段的比较器。这就是转发机制对控制冒险的辅助作用。 [笔记20]

---

**10. ( F ) 当 CPU 执行写操作并且 Cache 命中，写回（Write Back）策略可以让 Cache 和内存中的相应数据都更新。**

❌ 错误。Write Back（写回）策略在 Cache 命中时**只更新 Cache 中的数据**，并将该 Cache 行标记为"脏（dirty）"。只有当该 Cache 行被替换时才写回主存。题目描述的是 **Write Through（写直达）**策略——每次写操作同时更新 Cache 和主存。

## 二、（15 分）单周期数据通路——beq 指令

如图所示的单周期数据通路执行如下指令：

| Address (Byte) | Instruction |
|:---|:---|
| 100 | beq $R2, $R4, 7  # The address of register Rn is n, the value of the offset is 7 |

执行前：R1=12, R2=16, R3=8, R4=16

### a) (5 分) 将指令转换为 2 进制表示的 32 位机器码

**beq 指令格式（I 型）**：`op(6) | rs(5) | rt(5) | offset(16)`

- opcode(beq) = 000100
- rs = R2 = 00010₂
- rt = R4 = 00100₂
- offset = 7 = 0000 0000 0000 0111₂

```
31    26 25    21 20    16 15                               0
┌───────┬───────┬───────┬─────────────────────────────────┐
│ 000100│ 00010 │ 00100 │ 0000 0000 0000 0111             │
└───────┴───────┴───────┴─────────────────────────────────┘
  opcode   rs      rt              offset
```

**机器码**：`0001 0000 0100 0100 0000 0000 0000 0111₂` = `0x10440007`

**注**：MIPS 中 `beq` 的偏移量 = (目标地址 - PC - 4) / 4。此处题目直接给了 offset = 7（表示跳转 7 条指令），实际目标地址 = PC + 4 + 7 × 4 = 100 + 4 + 28 = **132**。

### b) (10 分) 填写数据通路信号值和控制信号值

**执行前状态**：
- PC = 100
- R2 = 16, R4 = 16（相等 → Zero = 1，分支成立）

| Signal | Value | 说明 |
|:---|:---|:---|
| **Register File** | Read Addr 1 | **2** | rs = R2，编号为 2 |
| | Read Addr 2 | **4** | rt = R4，编号为 4 |
| | Write Addr | **X** | beq 不写寄存器 |
| | Write Data | **X** | beq 不写寄存器 |
| RegWrite | | **0** | beq 不写寄存器堆 |
| ALUOp | (binary) | **01** | beq 做减法（比较相等），主控发出 ALUOp=01，ALU 控做 sub |
| MemtoReg | | **X** | beq 不写寄存器，无意义 |
| ALUSrc | | **0** | beq 的 ALU 第二操作数来自寄存器（rt），而非立即数 |
| Zero | | **1** | R2(16) - R4(16) = 0 → Zero = 1（分支成立） |
| The address to be stored in PC | | **132** | 分支成立：PC = (PC+4) + offset×4 = 104 + 28 = 132 |

**beq 数据通路关键路径** [笔记15-18, docs/wk11]：
1. PC → IMEM → 取指令 0x10440007
2. RegFile: Read Addr1=2 → Read Data1=16; Read Addr2=4 → Read Data2=16
3. ALU: 16 - 16 = 0 → Zero=1
4. Branch=1 AND Zero=1 → 与门输出=1 → PC 多路选择器选"分支目标地址"
5. 分支目标地址 = PC+4 + 符号扩展(offset)×4 = 104 + 7×4 = 132 → 写入 PC

## 三、（15 分）CPU 性能计算

在两个不同的 CPU 上，如非流水 CPU 和流水 CPU 上执行 15000 条指令，假定指令之间没有数据相关。

### a) (5 分) 非流水 CPU

- 非流水（单周期）CPU：每条指令 1 个时钟周期
- CPI = 1，时钟周期 = 3ns

$$
T_{\text{非流水}} = 15000 \times 1 \times 3\text{ns} = 45000\text{ns} = 45\mu\text{s}
$$

### b) (5 分) 流水 CPU

- 9 段流水线，时钟周期 = 0.4ns
- 流水线执行时间公式（k 段，n 条指令）：

$$
T_{\text{流水}} = k \times T + (n - 1) \times T = (k + n - 1) \times T
$$

其中第一项 $k \times T$ 是第一条指令从 IF 到 WB 填满流水线的时间，后续 $(n-1) \times T$ 是每个时钟完成一条指令的时间。

$$
T_{\text{流水}} = (9 + 15000 - 1) \times 0.4\text{ns} = 15008 \times 0.4\text{ns} = 6003.2\text{ns} \approx 6.0\mu\text{s}
$$

### c) (5 分) 加速比

$$
S_p = \frac{T_{\text{非流水}}}{T_{\text{流水}}} = \frac{45000}{6003.2} \approx 7.50
$$

**即 9 段流水线相对于单周期 CPU 的加速比约为 7.5 倍。**

> **理论极限**：理想加速比 = 流水线段数 = 9 倍。实际只有 7.5 倍，因为：
> 1. 第一条指令填满流水线用了 9 个时钟周期（起步开销）
> 2. 当 n 足够大时 $(k+n-1)/n \to 1$，加速比趋近于段数 k
> 3. 此例中 n=15000, k=9 → 理论=9×(15000/15008)=8.995 → 之所以是 7.5 而非 8.995，是因为**时钟周期从 3ns 变为 0.4ns 并不恰好是 9:1 的拆分**——单周期最慢路径决定了 3ns，流水线划分后每段 0.4ns（含流水寄存器开销）。
>
> 严格验证：若单周期 CPI=1, T=3ns；9 段流水 CPI≈1, T=0.4ns。加速比 = 3.0/0.4 × 1/1 = 7.5。这恰好等于时钟周期之比，说明 9 段并行带来的理论收益 = 实际加速比（因指令数足够多，k 的影响可忽略）。

## 四、（30 分）流水线数据冒险

假定如下的指令序列执行在 5 段流水上：

```
I1: add  $R2, $R1, $R3
I2: lw   $R1, 40($R2)
I3: addi $R4, $R1, -1
I4: and  $R4, $R1, $R2
```

### a) (10 分) 列出无转发和有转发情形下的所有数据冲突

**格式**：`R# from I# to I#`，表示寄存器 R# 在从指令 I# 到另一条指令 I# 时出现了数据冲突（RAW 读后写相关）。 [笔记20]

| Instruction sequence | Without Forwarding | With Forwarding |
|:---|:---|:---|
| I1: add $R2, $R1, $R3 | — | — |
| I2: lw $R1, 40($R2) | **R2 from I1 to I2** | **R2 from I1 to I2** |
| I3: addi $R4, $R1, -1 | **R1 from I2 to I3** | **R1 from I2 to I3** |
| I4: and $R4, $R1, $R2 | **R1 from I2 to I4** | **R1 from I2 to I4** |
| | **R2 from I1 to I4** | — |

**逐条分析：**

- **R2 from I1 to I2**：I1(add) 写 $R2 → I2(lw) 用 $R2 计算地址。无转发时 I2 需等 I1 的 WB（2 拍 stall）；有转发时，I1 的 ALU 结果在 EX/MEM → 转发到 I2 的 EX 段即可，**但 I2 在 EX 阶段需要 $R2 做地址计算，此时 I1 在 MEM 段，EX/MEM 流水寄存器中有 $R2 的新值 → 转发可以解决。** 等等——I1 的 EX 段完成后 $R2 在 EX/MEM 中，I2 的 EX 段需要在 ID/EX 锁存后的下一个时钟使用 ALU。时间线：I1 的 EX 在 cc3，结果进 EX/MEM；I2 的 EX 在 cc4。EX/MEM → I2 的 EX 输入（通过转发 MUX）→ **可以转发解决**。所以有转发时此项应能消除。

> **修正**：I1(EX) → I2(EX) 属于相邻指令的 RAW——I1 在 EX 段结束时将结果锁存到 EX/MEM，下一时钟 I2 进入 EX 段。通过转发路径将 EX/MEM 的 ALU 结果旁路到 I2 的 ALU 输入端 → **转发可消除**。因此有转发时 `R2 from I1 to I2` 不造成 stall。

重新整理：

| Instruction sequence | Without Forwarding | With Forwarding |
|:---|:---|:---|
| I1: add $R2, $R1, $R3 | — | — |
| I2: lw $R1, 40($R2) | **R2 from I1 to I2** | —（转发解决） |
| I3: addi $R4, $R1, -1 | **R1 from I2 to I3** | **R1 from I2 to I3**（load-use，转发不够） |
| I4: and $R4, $R1, $R2 | **R1 from I2 to I4** | —（转发解决，I2 的 MEM 数据 → I4 的 EX） |
| | **R2 from I1 to I4** | —（转发解决） |

**解释**：

- **R1 from I2 to I3**：这是 **load-use 冒险**。I2(lw) 在 MEM 段才拿到 $R1 的数据，I3(addi) 在 EX 段就需要 $R1。即使有转发，lw 的数据在 MEM 段结束时（时钟沿）才锁存到 MEM/WB，下一拍再转发到 I3——但 I3 的 EX 段在 I2 的 MEM 段的下一个时钟就用 ALU 了，时间差只有半个周期不够。**必须 1 stall**。

- **R1 from I2 to I4**：I2 在 MEM 段拿数据，I4 在 EX 段需要。时间线：I2(MEM)=cc4, I4(EX)=cc6。I2 的 MEM/WB 中有 $R1 新值 → 可转发到 I4 的 EX。距离足够，转发可解决。

- **R2 from I1 to I4**：距离更远，转发肯定可解决。

### b) (10 分) 插入最少量的 NOPs 以解决数据冒险

| Instruction sequence | Without Forwarding | With Forwarding, without hazard detection/stall |
|:---|:---|:---|
| add $R2, $R1, $R3 | add $R2, $R1, $R3 | add $R2, $R1, $R3 |
| lw $R1, 40($R2) | **nop** | lw $R1, 40($R2) |
| addi $R4, $R1, -1 | **nop** | **nop** |
| and $R4, $R1, $R2 | lw $R1, 40($R2) | addi $R4, $R1, -1 |
| | **nop** | and $R4, $R1, $R2 |
| | **nop** | |
| | addi $R4, $R1, -1 | |
| | **nop** | |
| | **nop** | |
| | and $R4, $R1, $R2 | |

**无转发时每个 RAW 冲突需要的 NOPs：**
- R2(I1→I2)：I1 写 $R2 在 WB(cc5)，I2 在 ID 需要 $R2(cc3-4) → 需让 I2 的 ID 等到 I1 的 WB 后 → 插入 **2 个 NOPs**
- R1(I2→I3)：load-use → **1 个 NOP**（实际上 load-use 也需要 2 个 NOPs 在无转发时，因为 lw 在 WB 才写回）
- R1(I2→I4)：距离更远，但 I3 的 NOPs 已经拉长了间距
- R2(I1→I4)：同样因前面 NOPs 已解决

**无转发最少 NOPs 版本（插入在相关指令之间）：**

```
add  $R2, $R1, $R3
nop                         # 等 $R2 写回
nop
lw   $R1, 40($R2)
nop                         # 等 $R1 写回（load-use）
nop
addi $R4, $R1, -1
nop                         # and 依赖 I3 的 $R4，但 I3 的 WB 与 I4 的 ID 可重叠
nop
and  $R4, $R1, $R2
```

> **详细原因**：无转发时，每条指令的结果必须等到 WB 段结束（写入寄存器堆）才能被后续指令使用。因此 I1(WB) 与 I2(ID) 之间差 3 拍（I1 的 EX/MEM/WB vs I2 的 IF/ID），需 2 NOP。I2(lw, WB) 与 I3(ID) 也需 2 NOP。I3 和 I4 同理。

**有转发但无冲突检测时**：只有 load-use（R1 I2→I3）无法被转发解决，需 1 个 NOP：

```
add  $R2, $R1, $R3
lw   $R1, 40($R2)
nop                         # load-use: 1 NOP
addi $R4, $R1, -1
and  $R4, $R1, $R2
```

### c) (10 分) 5 段流水 + 完整转发 + 冲突检测时空图

| | cc1 | cc2 | cc3 | cc4 | cc5 | cc6 | cc7 | cc8 | cc9 | cc10 |
|:---|:---:|:---:|:---:|:---:|:---:|:---:|:---:|:---:|:---:|:---:|
| add $R2,$R1,$R3 | IF | ID | EX | MEM | WB | | | | | |
| lw $R1,40($R2) | | IF | ID | EX | MEM | WB | | | | |
| addi $R4,$R1,-1 | | | IF | ID | **s** | EX | MEM | WB | | |
| and $R4,$R1,$R2 | | | | IF | **s** | ID | EX | MEM | WB | |

**详细解释** [笔记20]：

- **cc1-cc2**：正常取指流水。
- **cc3**：I1(EX) 的同时 I2(ID) 译码。冲突检测：I2 的 rs($R2) 和 I1 的 rd($R2) 匹配 → RAW 冲突，但 EX/MEM 转发路径可解决（I1 的 ALU 结果 → 转发 MUX → I2 的 ALU 输入）。
- **cc4**：I2(EX) 计算地址 $R2+40，I3(ID)。冲突检测：I3 的 rs($R1) 与 I2 的 rt($R1) 匹配（load-use）→ **硬件 stall**。PC 不更新，IF/ID 不写（I3 保持 ID 段），ID/EX 被清零（bubble）。气泡 = `s`。
- **cc5**：I3 保持在 ID（因 cc4 的 stall），I4 取指但被 stall 挡住（IF 停）。同时 I2 在 MEM 段读到 $R1 的新值。cc5 结束时，$R1 在 MEM/WB 中就绪。
- **cc6**：解除 stall。I3 在 ID 段从 MEM/WB 转发路径拿到 $R1 → 进入 EX。I4 进入 ID。转发解决 I3 对 $R1 的依赖（MEM/WB→I3 EX），以及 I4 对 $R1/$R2 的所有依赖。
- **cc7-cc10**：正常流水直至全部完成。

**总时钟周期数：10 个**（vs 无转发约 15+ 个，vs 理想无冲突 = 4+5-1 = 8 个）。只增加了 2 个气泡（1 个 load-use stall）。

## 五、（15 分）ID/EX 流水寄存器 — SW 指令

对于如下指令，填写出 ID/EX 流水寄存器中的内容：

```
2000  SW R16, 64(R12)   # 2000 is the address of the instruction
                        # the address of register Rn is n
                        # the contents of R12 and R16 are 60 and 80, respectively.
```

**（此题与 2023 年第四题完全相同，原题复用）**

**ID/EX 流水寄存器：**

| 类别 | 信号 | 值 | 说明 |
|:---|:---|:---|:---|
| **Data Path** | PC+4 | **2004** | PC + 4 |
| | Read data 1 | **60** | R[rs] = R[12] = 60（基址寄存器值） |
| | Read data 2 | **80** | R[rt] = R[16] = 80（要存储的数据） |
| | Signed extended lower 16 bits | **64** | 立即数 64 符号扩展为 32 位 |
| | Address of Rt | **16** | rt 寄存器编号 = 16 |
| | Address of Rd | **X** | SW 无 rd 字段 |
| **Control** | **EX** | ALUSrc | **1** | 第二 ALU 输入来自立即数（计算访存地址） |
| | | ALUOp (binary) | **00** | ALU 做加法 |
| | | RegDst | **X** | 无意义 |
| | **M** | Branch | **0** | 非分支指令 |

## 六、（15 分）Branch 偏移 + Cache 地址映射

### a) (3 分) 计算 loop 循环中 branch 指令的偏移地址

```asm
loop:   instr1       # 地址 4
        instr2       # 地址 8
instr3               # 地址 12
instr4               # 地址 16
BEQ R1, R0, <offset> # 地址 20（按字节编址，定长 4B）
continue...          # 地址 24
```

**分析**：
- BEQ 指令所在地址 = 16（题目标注 "BEQ 旁标 16"）
- MIPS 分支采用 PC 相对寻址：**跳转目标 = (PC + 4) + offset × 4**
- BEQ 执行时 PC = 16，PC + 4 = 20
- 目标地址 = loop = 4
- offset = (目标 - PC - 4) / 4 = (4 - 16 - 4) / 4 = (-16) / 4 = **-4**

$$
\text{offset} = \frac{\text{loop} - (\text{PC} + 4)}{4} = \frac{4 - 20}{4} = \frac{-16}{4} = -4
$$

16 位补码表示：`-4₁₀ = 1111 1111 1111 1100₂ = 0xFFFC`

**offset = -4**

> **关键理解** [笔记12]：MIPS 的 `beq` 偏移量以**指令条数**为单位（而非字节数），因为所有指令 4 字节对齐，低 2 位总为 0。指令字中偏移字段存的是跳转的指令数，电路自动左移 2 位（×4）得到字节偏移。计算时：offset = (目标地址 - PC - 4) / 4。

---

### b) (4 分) Cache 地址字段划分

2-路组相联 Cache，128 组，块大小 32 字节，32 位地址。

- **Byte offset**：块大小 32 字节 → $\log_2(32) = 5$ 位 → **bit4 ~ bit0**
- **Index**：128 组 → $\log_2(128) = 7$ 位 → **bit11 ~ bit5**
- **Tag**：剩余高位 → 32 - 5 - 7 = 20 位 → **bit31 ~ bit12**

| Tag | Index | Block offset | Byte offset |
|:---|:---|:---|:---|
| bit31 ~ bit**12** | bit**11** ~ bit**5** | bit**4** ~ bit**2**? | bit**1** ~ bit0? |

**注意**：题目表格中"Block offset"和"Byte offset"分列——通常"Block offset"指块内字的偏移，"Byte offset"指字内字节偏移。但由于块大小 = 32 字节，若按 32 位（4 字节）字编址：

- Byte offset（字内字节）：2 位 → bit1 ~ bit0
- Block offset（块内字）：3 位（32 字节 ÷ 4 字节/字 = 8 字）→ bit4 ~ bit2

**更合理的划分**（按字节编址，但区分块内偏移的层次）：

| Tag | Index | Block offset | Byte offset |
|:---|:---|:---|:---|
| bit31 ~ bit**12** | bit**11** ~ bit**5** | bit**4** ~ bit**2**? | bit**1** ~ bit0? |

实际上在按字节编址的 32 位系统中，Cache 块 32 字节，"Block offset"通常就是指整个 5 位块内偏移（bit4-0）。如果要细分——"Block offset"为块内字偏移（bit4-2，3 位含 8 个 4 字节字），"Byte offset"为字内字节偏移（bit1-0，2 位含 4 字节），但这不是通用做法。

**按常规理解**（5 位块内偏移一次性处理）：

| Tag | Index | Block offset | Byte offset |
|:---|:---|:---|:---|
| bit31 ~ bit**12** | bit**11** ~ bit**5** | bit**4** ~ bit**2** | bit**1** ~ bit**0** |

> **注**："Block offset"与"Byte offset"的区分方式取决于教材定义。有些教材将块内偏移统称为 Block offset = 5 位（bit4-0），有些则拆分为块内字偏移 + 字内字节偏移。建议以课堂 PPT 为准。课堂讲 Cache 时，通常将块内直接称为 Block offset = $\log_2(\text{块大小/字节})$。

### c) (4 分) Cache 容量（以 bit 为单位）

2-路组相联，128 组，块大小 32 字节，每行 1 有效位。

- 总行数 = 128 组 × 2 路 = **256 行**
- 每行 Tag 位数 = 20 位
- 每行数据 = 32 字节 = 32 × 8 = 256 位
- 每行有效位 = 1 位

每行容量 = 1 + 20 + 256 = **277 位**

总容量 = 256 × 277 = **70,912 位**

$$
\text{Cache 容量} = 256 \times (1 + 20 + 32 \times 8) = 256 \times 277 = 70912 \text{ bit}
$$

≈ 8.66 KB（70912 / 8 / 1024）

> **注**：此处不含 LRU 位（2-路组相联每组的 LRU 需 1 位/组，128 位），不含 dirty 位（写回策略才需要）。

### d) (4 分) 改为直接映射后的 Index 位数

条件：Cache 总大小不变（70912 bit），块大小改为 **8 字节**，仍 32 位地址，直接映射。

**先求新 Cache 的行数：**

设新 Cache 有 N 行，块大小 8 字节 = 64 位。

- 新 Index 位数 = $\log_2(N)$
- 新 Tag 位数 = 32 - Index - 3（Byte offset 3 位，因 8 字节）
- 每行 = 1（有效位）+ Tag + 64（数据位）

总容量不变：
$$N \times (1 + (32 - 3 - \log_2 N) + 64) = 70912$$
$$N \times (94 - \log_2 N) = 70912$$

试算：
- 若 Index = 10（N = 1024）：1024 × (94 - 10) = 1024 × 84 = 86016 位 > 70912
- 若 Index = 9（N = 512）：512 × (94 - 9) = 512 × 85 = 43520 位 < 70912

所以 N 介于 512~1024 之间。精确求解：

$$N \times (94 - \log_2 N) = 70912$$

设 N = 2^i：
$$2^i \times (94 - i) = 70912$$

| i | N | 94-i | 乘积 |
|:---|:---|:---|:---|
| 9 | 512 | 85 | 43520 |
| 10 | 1024 | 84 | 86016 |
| ν | ~845 | ~83.7 | 70912 |

设 i = 9.7 → 94 - 9.7 = 84.3 → N ≈ 70912 / 84.3 ≈ 841。
$2^{9.7} ≈ 831$。反复逼近：N = 831, i ≈ 9.7。

取 **Index = 10 位**（N = 1024）——实际容量 86016 位，比原来的 70912 位略大。

> **关键**：Index 需要 10 位来表示。验证：每行 Tag = 32 - 10 - 3 = 19 位。

若严格保持总容量 70912 位不变：
每行 = 1 + Tag + 64 = 1 + (32 - 3 - i) + 64 = 94 - i
N = (总容量) / (94 - i)

精确解 N = 831 时：$\log_2(831) \approx 9.7$，即 Index ≈ 10 位（需要上取整）。

**地址划分（新 Cache，直接映射，行数可容纳原来的全部数据位）：**

| Tag | Index | Block offset | Byte offset |
|:---|:---|:---|:---|
| bit31 ~ bit**13** | bit**12** ~ bit**3** | bit**2** ~ bit**0**? | — |

若 Index = 10: bit12 ~ bit3, Tag = bit31 ~ bit13（19 位）。

**简化回答**：直接映射方式下，Index 需要 **10 位**（可寻址最多 1024 行），占据地址的 bit12 ~ bit3。
